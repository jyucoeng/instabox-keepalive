# instabox-keepalive

让 InstaBox 免费机**不被自动休眠**、也**不撞 2 小时强制挂起**的 Cloudflare Worker。

不用自己的机器常开，一个 Worker 能带多个账号，免费额度用不到 3%。

**当前版本 `v1.3.0`** —— 访问 `/status` 或 `/accounts`，返回里第一个字段就是 `version`，线上跑的是哪一版一眼可见。

---

## 一、它对付的是哪两条限制

InstaBox 免费机有两条硬规矩，续租只能解决第一条：

| 平台限制 | 后果 | 这个 Worker 怎么做 | 要配吗 |
| --- | --- | --- | --- |
| 空闲 30 分钟 | 自动休眠 | cron 每 5 分钟续一次活动租约（TTL 900 秒） | 不用，部署即生效 |
| 连续跑满 **2 小时（120 分钟）** | 强制挂起 + 冷却**约 14 分钟** | 剩 20 分钟时自己 `suspend → resume` 一次，把计时清零 | 不用，默认开 |

第二条是重点，也是最容易搞错的地方（很多地方写 8 小时，是错的）：

- **上限是 2 小时**。实测：`runStartedAt` 之后正好 **120 分 00 秒**被挂，冷却 **14 分 11 秒**，期间续租和 resume 全部返回 `409 machine_cooldown`。
- **保活靠的是"提前量"兜底，不是那几个整点**。默认 `INSTABOX_CYCLE_MARGIN_MIN=20`，即每 **100 分钟**必轮一次（实测间隔稳定在 5995–6001 秒）。
- `INSTABOX_CYCLE_AT` 那四个点只是把轮转时刻**锚定**在固定整点，让你能预知什么时候会断 2–3 秒。删了机器也不会死，只是断线时刻开始漂移。

> ⚠️ `INSTABOX_CYCLE=0` **不是**"只保活不轮转"，而是**关掉整个轮转**（定时点和提前量都不触发）。
> 机器会一路跑到 120 分钟被平台挂起，冷却约 14 分钟才恢复，前后停机十几分钟。想减少轮转次数请调 `INSTABOX_CYCLE_MARGIN_MIN`，别关 `INSTABOX_CYCLE`。

## 二、部署（网页面板，5 分钟）

不用装 wrangler。

**只要两步就能跑**，其余全有默认值。

1. **建 Worker + 贴代码**：面板 → `Workers & Pages` → `Create` → `Worker` → 起名 → `Deploy`
   → `Edit code`，把 `worker/worker.js` 全文覆盖进去 → `Deploy`
2. **加 key**：`Settings` → `Variables and Secrets`，存一条 **Secret**
   `INSTABOX_API_KEY` = 你的 `ibk_...`（多个账号再加 `INSTABOX_API_KEY_2` / `_3`）
3. **加定时**：`Settings` → `Triggers` → `Cron Triggers`，填 `*/5 * * * *`
   > `*/5` 是按钟表对齐的（`:00/:05/:10…`），不是"上次跑完 +5 分钟"。

到这里就能保活了。下面两个是加分项：

4. **（建议）加口令**：存一条 Secret `TOKEN` = 随机串（`openssl rand -hex 16`）。
5. **（可选）绑 KV 看日志**：`Storage & Databases` → `KV` → 建 namespace，回 Worker 的 `Bindings` 加绑定，**变量名必须叫 `LOG`**。不绑也能跑，只是 `/log` 是空的。

> **不需要配任何 `INSTABOX_CYCLE_*` / `INSTABOX_LEASE_TTL` / `INSTABOX_ANON`。**
> 那些都有默认值，且默认值就是推荐值。配得越多越容易把自己配坏。

- `"nextCycleAt"` 有值 —— 轮转已经排上了

```sh

```

## 四、一次轮转发生了什么

以 `19:00` 那次为例（抖动默认全关）：

```text
19:00:0x  cron 触发 → 判定：到点了 + 机器在跑 + 这个点之后还没重启过
19:00:0x  POST /suspend
19:00:1x  确认 suspended
19:00:1x  POST /resume（失败自动用 /start 兜底）
19:00:2x  确认 running
19:00:2x  PUT 活动租约（生命周期操作会让旧租约失效，必须补一次）
```

几个要点：

- **停多久**：每台 10–30 秒。默认 `CYCLE_HOLD_SEC=0`，就是"确认睡下立刻叫醒"。进程通常保留（`runtime.processesPreserved`）
- **多台错峰**：一次 cron 只轮转一台（一轮约 20 个子请求，免费版单次上限 50）。3 台就是 19:00 / 19:05 / 19:10
- **兜底**：某个点没赶上（正在部署、Worker 抖动），剩余时间掉到 20 分钟时会立刻补一次
- **手动触发**：`GET /?token=xxx` 走同一套判断，想立刻轮不用等 cron
- **同一个点只转一次**：靠 `runStartedAt` 和点比较，不需要额外存状态

## 五、想改才看

### 只续租、不轮转

```
INSTABOX_CYCLE = 0
```

**这是关掉全部轮转的开关**（定时点和提前量都不触发）：机器会一路跑到 120 分钟 → 平台挂起 → 冷却约 14 分钟 → 自动恢复。前后停机十几分钟，只有"宁可停机也不许机器重启"的场景才这么用。

### 换轮转时间点

```
INSTABOX_CYCLE_AT = "01:30,13:00"   # 本地时间，逗号分隔
INSTABOX_CYCLE_TZ = "Asia/Shanghai"
```

**前提**：上限只有 2 小时，所以任何"一天只放几个点"的方案都盖不住整个周期 ——
保活永远靠 `MARGIN` 兜底（每 100 分钟一轮），这些点只决定"额外的轮转落在哪个整点"。

默认值 `01:30,13:00` 就是推荐值，**这一项你不需要改**。往下看整日表就知道为什么。

想减少轮转次数，改的是 `INSTABOX_CYCLE_MARGIN_MIN`（提前量越小轮得越少、但越贴近上限），
不是删时间点。

### 为什么默认留这 2 个锚点

**先说清楚一件事**：把 `INSTABOX_CYCLE_AT` 留空，**不等于**"不要锚点"——
空串会回落到 `DEFAULT_CYCLE_AT`（还是 `01:30,13:00`）。代码里没有任何配置能让时间点真的消失。

那为什么还要留着它们？

#### 一、兜底会漂，锚点负责把漂移归零

兜底间隔是死的：上限 120 分钟 − 提前量 20 分钟 = **每 100 分钟一轮**。
但一天是 1440 分钟，`1440 ÷ 100 = 14.4` —— **除不尽**。

后果是纯兜底时，轮转时刻每天往后错 40 分钟：

```
今天   03:10  04:50  06:30  08:10 ...
明天   03:50  05:30  07:10  08:50 ...
一周后 07:50  09:30  11:10  12:50 ...
```

一周就漂了 4 个多小时，一个月能漂掉大半天。**这时候日志里的时间戳毫无参考价值**——
你没法说"这个点该转没转"，因为根本没有"该"的时刻。

锚点的作用就是在固定整点强制插一次轮转，把累积的漂移**归零**。

#### 二、为什么是 2 个，不是 1 个或 4 个

| 锚点数 | 漂移情况 | 代价 |
| --- | --- | --- |
| 0 个（纯兜底） | 每天 +40 分钟，无限累积 | 时刻完全不可预测 |
| 1 个 | 只在一天里纠错一次 | **那次若错过，一整天就白漂了** |
| **2 个（默认）** | 每半天归零一次，最大漂移约 20 分钟 | 多约 1.6 次重启/天 ≈ 4 秒 |
| 3~4 个（旧默认） | 漂移更小 | 重启次数没减，锚点密集到跟兜底没区别 |

关键在第三行那个加粗：**锚点会错过**。它只在 `CYCLE_WINDOW_MIN=30` 分钟的窗口内生效，
且要求到点时机器正好在 `running`。窗口错过了就等下一个——所以至少要 2 个，才有冗余。

#### 三、为什么偏偏是 01:30 和 13:00

- **相隔 11.5 小时（690 分钟）**：`690 ÷ 100 = 6.9`，不是整数倍，不会和兜底周期共振
  （如果正好隔 600 或 700 分钟，锚点会永久性地卡在某个兜底点旁边，等于白配）
- **半夜 01:30 / 午休 13:00**：一天里人工操作最少的两个时段，真被撞上也不影响你
- 两个点把一天切成"长 11.5 小时 + 短 12.5 小时"两段，任何时刻距离最近的锚点都不超过半天

#### 四、真要极限省次数怎么办

那就别动时间点，动提前量：

```
INSTABOX_CYCLE_MARGIN_MIN = "15"    # 每 105 分钟一轮，一天约 13.7 次
```

代价是离 120 分钟上限只剩 15 分钟余量，机器数量一多（排队要 (N−1)×5 分钟）就容易撞线。
3 台以内用 15 是安全的，4 台以上别低于 20。

### 默认方案一天长这样（`01:30,13:00` + 提前量 20 分钟）

上限 120 分钟、剩 20 分钟就轮转，所以两次兜底之间固定是 **100 分钟**；两个锚点会把漂移拉回整点，
代价是那两次间隔变短（90 分钟 / 50 分钟）。

| 时刻 | 触发原因 | 距上次重启 | 说明 |
| --- | --- | --- | --- |
| **01:30** | 锚点 | 50 分钟 | 把漂移拉回整点 |
| 03:10 | 兜底 | 100 分钟 | 离上限还剩 20 分钟 |
| 04:50 | 兜底 | 100 分钟 | |
| 06:30 | 兜底 | 100 分钟 | |
| 08:10 | 兜底 | 100 分钟 | |
| 09:50 | 兜底 | 100 分钟 | |
| 11:30 | 兜底 | 100 分钟 | |
| **13:00** | 锚点 | 90 分钟 | 比兜底早 10 分钟，拉回整点 |
| 14:40 | 兜底 | 100 分钟 | |
| 16:20 | 兜底 | 100 分钟 | |
| 18:00 | 兜底 | 100 分钟 | |
| 19:40 | 兜底 | 100 分钟 | |
| 21:20 | 兜底 | 100 分钟 | |
| 23:00 | 兜底 | 100 分钟 | |
| 00:40 | 兜底 | 100 分钟 | 跨日 |
| **01:30** | 锚点 | 50 分钟 | 回到起点，循环 |

- **一天 16 次，每次中断 2–3 秒**（实测 `Paused → Resumed` 间隔 2.4–3.0 秒），全天累计停机约 **40 秒**
- 最长的连续运行是 100 分钟，离 120 分钟上限始终留 20 分钟余量
- **实际触发时刻会有 0–5 分钟误差**：cron 每 5 分钟才跑一次，落在哪个 tick 看运气（比如 03:10 可能实际 03:10 或 03:15）
- 多台机器会错开，因为每轮 cron 只轮转一台：3 台同时到期时是 T+0 / T+5 / T+10

懒得算就只报高峰时段，让它自己排：

```
INSTABOX_PEAK_HOURS = "10-12,14-18,20-23"
```

会排成 `00:00,06:00,12:00,18:00`（全在高峰外、间隔 6 小时）。`/accounts` 里能看到排出来的结果和来源（`cycleAtSource: "auto"`）。

### 多账号

**规则一句话**：第 N 个账号 = 变量名加 `_N` 后缀。加账号就是多存一个 Secret，别的都不用动。

#### 3 个账号长这样（就是这个项目当前的配置）

在 `Settings → Variables and Secrets` 里，一共 4 条 Secret：

| 变量名 | 类型 | 值 | 对应 |
| --- | --- | --- | --- |
| `INSTABOX_API_KEY` | Secret | `ibk_1a2b3c4d…` | 第 1 个 InstaBox 账号的 key |
| `INSTABOX_API_KEY_2` | Secret | `ibk_5e6f7a8b…` | 第 2 个账号的 key |
| `INSTABOX_API_KEY_3` | Secret | `ibk_9c0d1e2f…` | 第 3 个账号的 key |
| `TOKEN` | Secret | `••••••••••••••` | 访问口令，自己定 |

可选第 5 条：KV 绑定 `LOG`（看日志用，不绑也能跑）。

里面没有一个 `INSTABOX_CYCLE_*`——那些全走默认值。

#### 想加到 4 个、5 个、10 个账号

**加一行就行**，表里照抄：

| 你要几个账号 | 需要增加的变量 | Secret 总数（含 TOKEN） |
| --- | --- | --- |
| 1 个 | `INSTABOX_API_KEY` | 2 |
| 2 个 | 再加 `INSTABOX_API_KEY_2` | 3 |
| **3 个** | 再加 `INSTABOX_API_KEY_3` | **4** ← 当前 |
| 4 个 | 再加 `INSTABOX_API_KEY_4` | 5 |
| 5 个 | 再加 `INSTABOX_API_KEY_5` | 6 |
| 10 个 | 一直加到 `INSTABOX_API_KEY_10` | 11 |
| N 个 | 一直加到 `INSTABOX_API_KEY_N` | N + 1 |

具体到 5 个账号的样子：

| 变量名 | 值 |
| --- | --- |
| `INSTABOX_API_KEY` | `ibk_1a2b3c4d…`（账号 1） |
| `INSTABOX_API_KEY_2` | `ibk_5e6f7a8b…`（账号 2） |
| `INSTABOX_API_KEY_3` | `ibk_9c0d1e2f…`（账号 3） |
| `INSTABOX_API_KEY_4` | `ibk_你的第4个key…`（账号 4） |
| `INSTABOX_API_KEY_5` | `ibk_你的第5个key…`（账号 5） |
| `TOKEN` | `••••••••••••••` |

#### 别踩的坑

- **编号可以不连续**：只配 `_2` 和 `_3`、跳过 `_1` 也能跑（`_1` 等同不带后缀）
- **`INSTABOX_MACHINE` 会被继承**：两个账号机器名不同时，记得单独写 `INSTABOX_MACHINE_2`，
  否则 2 号账号会用 1 号的机器名去找机器
- **同一把 key 配两次只续一次**，不会重复轮转
- **某个账号 key 失效不影响其它账号**，日志里会单独标 `FAIL`
- 账号多了注意排队：每轮 cron 只轮一台，N 台同时到期时要 `(N−1)×5` 分钟。
  3 台还剩 10 分钟余量，4 台剩 5 分钟，**5 台以上要自己算一下 `INSTABOX_CYCLE_MARGIN_MIN`**

#### 验证

```sh
curl "https://<你的worker>/accounts?token=<你的TOKEN>"
```

看到 `#1` `#2` `#3` 三行（key 已打码）就说明都认到了。

### 安全

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `TOKEN` | 空 | 配了之后所有请求带 `?token=`，错了返回 `401` |
| `INSTABOX_ANON` | `readonly` | **只在没配 `TOKEN` 时生效**：`readonly` 只放 `/status` `/accounts` `/log`（挡住能触发写操作的 `/` 和 `/release`）、`open` 全放行（v1.2.0 及以前的行为）、`closed` 全 `403` |

不配 `TOKEN` 也能跑（和旧版一致），但任何人知道域名就能触发续租/释放、刷光 KV 日志额度。建议配上。

## 六、接口

```text
GET /?token=xxx            所有账号各续租一次（cron 跑的就是这个逻辑）
GET /status?token=xxx      机器状态
GET /accounts?token=xxx    配了哪些账号（key 打码）
GET /log?token=xxx         最近 48 条日志
GET /release?token=xxx     放掉租约
```

都支持 `&account=2` 只看 2 号账号、`&format=text` 输出纯文本。

`/status` 每台机器带这些字段：

| 字段 | 含义 |
| --- | --- |
| `state` | `running` / `suspended` / `stopped` |
| `runStartedAt` | 本轮连续运行的起点。**轮转成功会跳变，这是验证轮转是否真生效的关键** |
| `remainingMinutes` | 离 2 小时上限还剩几分钟（上限 120） |
| `cooldownUntil` | 冷却到什么时候（没冷却为 `null`） |
| `nextCycleAt` | 下次轮转时间 |

`/` 的结果里，被轮转的机器带 `"cycled": true`、`"trigger": "slot"`（定时）或 `"limit"`（兜底）。

| `INSTABOX_CYCLE_JITTER_MIN` | `0-0` | 开始时间抖动，如 `0-15` 表示到点后晚 0–15 分钟 |
| `INSTABOX_CYCLE_HOLD_SEC` | `0-0` | 停机时长，如 `600-900`。**超过 600 秒必须绑 KV** |
| `INSTABOX_WAKE_JITTER_MIN` | `0-0` | 冷却结束后再随机等几分钟 |

## 八、常见问题

**为什么不能直接把自动休眠关掉？**

2026-10-18 实测：账号级 `fixedAutoSuspendSeconds: 1800`、`manualLifecycle: false`，服务端把空闲阈值锁死。对 `PATCH /v1/machines/{id}` 传 `autoSuspendAfterSeconds: 0`（含官方 CLI 和 SDK）一律返回 200，但值不变 —— 静默忽略。所以只能走租约这条官方口子。

**为什么不在机器里跑定时任务？**

机器一 suspend，里面的 cron / systemd timer 全冻住，叫不醒自己。续租必须来自**外部**，这就是放在 Cloudflare Worker 上的原因。

**免费额度够吗？**

- **子请求**：每次调用上限 50 个。一个账号约「1 次列机器 + 每台 1 次续租」，一次轮转约 20 个。3 账号各 1 台用不到 10 个
- **KV 写**：每天 1000 次。默认 `hourly` 每天约 24 次，占 2.4%；多账号也是一条日志装全部
- cron 别改成 `* * * * *`（1440 次/天），会把 KV 写额度刷光

**机器上的任务必须连续跑超过 2 小时？**

免费版做不到 —— 120 分钟是硬上限。要么拆任务（每 100 分钟断 2–3 秒，任务能续跑就不怕），
要么升级付费版（`maxRunMinutes = -1`，不限）。
`INSTABOX_CYCLE=0` 不是解法，那只会让机器每 2 小时被平台挂 14 分钟。

**机器变多了要改什么？**

不用改 —— 提前量会自己加宽。因为每轮 cron 只轮转一台，N 台同时进窗口时排在后面的要等：

| 账号/机器数 | 实际提前量 | 最后一台轮完时离上限还剩 |
| --- | --- | --- |
| 1–3 台 | 20 分钟（不变） | 10 分钟以上，安全 |
| 4 台 | 自动升到 25 | 5 分钟，够 |
| 5 台 | 自动升到 30 | 5 分钟，够 |

公式是 `max(你配的 MARGIN, 10 + (N-1)×5)`。所以加到 4、5 台都不用动配置，
但**别手动把 `INSTABOX_CYCLE_MARGIN_MIN` 调小**，那会抵消这个自动加宽。

**改了 cron 间隔要注意什么？**

`LEASE_TTL` 必须跟着调大，否则两次续租之间会空窗。`*/5` 配 900 有余量；拉到 15 分钟以上就要同步改 TTL。

## 九、版本历史

改了行为就往上走一位：MAJOR = 机制变了（影响别人怎么用）、MINOR = 行为或默认值变了、PATCH = 只改文案注释。
`/status` 和 `/accounts` 的返回里都带 `version`，不用去翻 Cloudflare 的部署历史。

| 版本 | 对应 tag | 变化 |
| --- | --- | --- |
| `v1.3.0` | tag `v1.3.0` | **配置精简**：`INSTABOX_ANON` 默认值 `open` → `readonly`；面板从 14 项降到 5 项（3 把 key + `LOG` + `TOKEN`），其余全部走代码默认值 |
| `v1.2.0` | tag `v1.2.0` | 默认锚点 `01:30,08:00,13:00,19:00` → `01:30,13:00`；响应统一带 `version`；补 `INSTABOX_ANON` 用法 |
| `v1.1.0` | tag `v1.1.0` | **实测把上限口径从 8 小时改成 2 小时**（120 分 00 秒被挂、冷却 14 分 11 秒）；`isNotRunning` 增认 `machine_cooldown`；提前量按账号数自适应 `max(MARGIN, 10+(N-1)×5)` |
| `v1.0.0` | tag `v1.0.0` | 初版：按 8 小时上限设计的时间点轮转 + 提前量兜底 |

> `v1.0.0` 里"8 小时"的说法是错的（当时只看了文档没实测）。真实上限 120 分钟，`v1.1.0` 起全部按 2 小时算。
